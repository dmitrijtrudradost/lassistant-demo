# EXP-001 — паритет извлечения DOCX

Дата: 2026-08-09  
Документ: `dogovor_0005.docx`  
Gold: `dogovor_0005.json`  
Модель: `models/contract-ner/ner_model_final`

## Вывод

Гипотеза NER-001 подтверждена количественно. Склейка ячеек через ` | ` была
основной причиной путаницы сторон и захвата соседних реквизитов адресом.

| Метрика | Training-compatible | Старый C# extraction | Новый C# NER extraction |
|---|---:|---:|---:|
| Role/text multiset F1, 10 weak roles | 0.8148 | 0.2857 | 0.8148 |
| Party confusion | 0% | 6.8% (3 случая) | 0% |
| Address overcapture | 0% | 80% | 0% |
| Средний score | 0.7020 | 0.4473 | 0.7020 |
| Число сущностей после postprocess | 94 | 145 | 94 |
| `text != raw_text[start:end]` | 0 | 0 | 0 |

Новый C#-вход совпал с `python-docx` побайтово после декодирования UTF-8:

```text
equal: true
characters: 25446
fragments: 369
```

Для метрик использован default Python postprocess без C#-агрегатора: агрегатор
намеренно не включён, поскольку он удаляет повторные вхождения и делает
entity-level precision/recall несопоставимыми. На обоих вариантах входа
пайплайн был одинаковым.

## Что изменено

- Существующий `DocxPlainTextExtractor.Extract()` оставлен для UI.
- Добавлен `ExtractForNer()`: body paragraphs, затем таблицы, ячейки и nested
  tables; один paragraph на фрагмент, без объединения колонок.
- Обработаны `TabChar`, текстовые `Break`, page break и lone surrogates в
  соответствии с поведением `python-docx paragraph.text`.
- Каждый фрагмент содержит offsets и координаты `table/row/cell/column`.
- Текст и metadata передаются в Python отдельными полями JSON, поэтому
  служебные идентификаторы не попадают в токены модели.
- Для таблиц party определяется по колонке/ячейке. Неоднозначная таблица
  возвращает `party_hint = null`, а не наследует последнюю сторону.
- Перед инференсом сохраняются `diagnostics/contract-ner/input.txt` и
  `input.fragments.json`.

## Уточнение после аудита артефактов

Первый прогон обнаружил независимый дефект: HuggingFace `entity["word"]`
вставлял пробелы вокруг знаков препинания, хотя offsets были корректны.
Формирование поля `text` заменено на точный срез `raw_text[start:end]`.
Повторная проверка всех вариантов дала 0 несовпадений.

`NerSpanToTemplateConverter` также переведён на offsets: текст для замены
извлекается из сохранённого NER-входа, а отображаемое `entity.Text` больше не
является источником истины.
Отдельная интеграционная проверка production-режима с C#-агрегатором:
42 итоговые сущности, 0 нарушений `text == input[start:end]`.

Версии `postprocess.py` приложения и Task 2.5 до правок были идентичны:

```text
SHA256 C8768B81AACEC2B3421789BAE9CF8899FE1B461C0D8ED263673E93F5EB16C948
```

Следовательно, остаточные конфликты были реальными. Добавлены два точечных
правила:

- одинаковый span не может одновременно быть `объект_тип` и
  `*_город_банка`; сохраняется банковский город;
- одинаковый номер одной стороны не может одновременно быть расчётным и
  корреспондентским счётом; сохраняется вариант с большим score.

После правил ложный `объект_тип = Кострома` удалён, а номер
`35879006356990003281` остался только `исполнитель_корр_счет`. F1
по role/text вырос с 0.6875 до 0.7333. Финальная точная дедупликация
`(start, end, role)` устранила три повторных предсказания и повысила
диагностический role/text F1 до `0.8148`. Эта метрика не является exact span F1:
gold JSON использует другую сериализацию текста и несовместимые offsets.
Финальная сверка методов и доверенная метрика приведены в
[`EXP001_FINAL_RECONCILIATION_2026-08-09.md`](EXP001_FINAL_RECONCILIATION_2026-08-09.md).

## Проверка реальным договором

Полный инференс выполнен на
`КГ 2025-09-25 Д 03-КМ.docx`. Ошибок процесса и кодировки нет; реквизиты
двух колонок получили разные структурные party hints. При этом модель всё ещё
ошибается на непривычной семантике реального документа (например, отдельные
ложные роли и адрес с ИНН внутри одного исходного paragraph). Эти ошибки уже
не вызваны склейкой ячеек и относятся к следующим этапам улучшения корпуса и
postprocess.
